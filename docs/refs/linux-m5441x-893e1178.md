# Linux MCF5441x evidence, commit 893e11787f78

Cross-checks the emulator's MCF5441x MMIO facts against upstream Linux, which
carries an in-tree `arch/m68k` platform for this exact SoC family and is
independent of the MCF5441XRM.pdf extraction already cited in `emu/*.py`.

Source: `torvalds/linux`, commit `893e11787f78e43b534e252249ac3fff4d1333f8`
(2026-09-08, "Merge tag 'x86_urgent_for_7.3-rc3' ..."), fetched as a sparse
clone:

```sh
git clone --filter=blob:none --sparse https://github.com/torvalds/linux /tmp/linux-m5441x
cd /tmp/linux-m5441x
git checkout 893e11787f78e43b534e252249ac3fff4d1333f8
git sparse-checkout set arch/m68k drivers/mmc/host/sdhci-esdhc-mcf.c drivers/mmc/host/sdhci-esdhc.h
```

GPL-licensed source is cited here only as file/line references and short
paraphrase; no Linux source text is copied into this repository.

Every fact below is labeled:

- **HW** -- a hardware/register fact (address, bit, offset) that Linux and
  the emulator both encode, independent of any OS policy.
- **QUIRK** -- a hardware *behavior* that only shows up because a Linux
  driver had to work around it (e.g. a non-standard bit position). Still a
  hardware fact, but one that would be easy to miss from the register map
  alone.
- **POLICY** -- a Linux OS/RTOS choice (priority number, task-stack
  handling, driver init order) that says nothing about what the firmware in
  this repo does or must do.

## 1. Interrupt controllers (HW, confirmed match)

`arch/m68k/include/asm/m5441xsim.h:36-49`: three 64-source controllers.

    MCFINT_VECBASE   = 64
    MCFINTC0_ICR0    = 0xfc048040   INTC0 vector base 64
    MCFINTC1_ICR0    = 0xfc04c040   INTC1 vector base 128
    MCFINTC2_ICR0    = 0xfc050040   INTC2 vector base 192

Matches `emu/pit.py:90-91` (`INTC = ((0xFC048000, 64), (0xFC04C000, 128),
(0xFC050000, 192))`, `ICR_BASE = 0x40`) exactly, including the base
addresses (ICR0 = base + 0x40).

`arch/m68k/coldfire/Makefile:32`: `CONFIG_M5441x` builds `intc-simr.o`, not
`intc-2.o`. This matters (QUIRK): `intc-simr.c`'s `intc_irq_startup` writes
the *raw level* into the ICR byte (`mcf_write8(5, ...ICR0 + irq)`,
`arch/m68k/coldfire/intc-simr.c:118-124`), whereas the `intc-2.c` family
(523x/527x/528x/547x/548x) encodes `level<<3 | priority`
(`arch/m68k/coldfire/intc-2.c:32-33`). `emu/pit.py:132`
(`icr = ...[0] & 0x07`) assumes the raw-level (simr) encoding, which is the
one that applies to the MCF5441x. Confirmed correct, and worth citing
because guessing the wrong INTC family here would silently misread every
ICR byte.

`intc-simr.c` masks/unmasks sources through single-byte `SIMR`/`CIMR`
registers at INTC base + 0x1C/0x1D (write source number to set/clear one
mask bit), not through the 32-bit `IMRH`/`IMRL` registers at + 0x08/+0x0C
that `emu/pit.py:133-135` and `emu/dtim.py` read directly. **Open
question**: Linux's driver never exercises IMRH/IMRL, so this doc cannot
confirm or deny their offset from Linux; that fact still rests solely on
MCF5441XRM.pdf chapter 17. Both register views plausibly alias the same
mask bits (a common ColdFire INTC pattern), but that is not established by
this commit.

## 2. PIT timers (HW, confirmed match)

`arch/m68k/include/asm/m5441xsim.h:104-114`:

    MCFPIT_BASE0..3 = 0xFC080000, 0xFC084000, 0xFC088000, 0xFC08C000
    MCFINT2_PIT0..3 = 13, 14, 15, 16   (INTC2 sources)

so vectors are 192+13..16 = 205..208. Matches `emu/pit.py:81-82` (`BASES`,
`VECTORS = (205, 206, 207, 208)`) exactly.

Clock domain (HW): `arch/m68k/coldfire/m5441x.c:41-44` --
`DEFINE_CLK(0, "mcfpit.0", 32, MCF_BUSCLK)` through `mcfpit.3`, all four PITs
clocked from `MCF_BUSCLK`. `MCF_BUSCLK = MCF_CLK / 2`
(`arch/m68k/include/asm/m5441xsim.h:15`). Matches `emu/pit.py`'s
`F_BUS = 132_000_000` being the *bus* clock (core/2), and the module
docstring's "three independent timers landing on round numbers ... validates
the 132 MHz bus clock" claim.

`arch/m68k/coldfire/pit.c` (the generic PIT clockevent driver Linux uses on
5270/5271/5282/5208, not wired for `CONFIG_M5441x` per the Makefile) is
useful only as corroboration of the *register field* semantics --
`MCFPIT_PCSR_EN`, `_PIE`, prescale-by-shift -- since no in-tree PIT
clockevent/clocksource driver is actually instantiated for this machine
(`m5441x.c`'s `config_BSP` still calls `hw_timer_init`, so Linux does drive
PIT1 as its system tick on this SoC, just through the shared `pit.c`, not a
5441x-specific file). This is IP-block corroboration of the field layout,
not new address evidence beyond what section's already stated above.

## 3. DTIM / DMA timers (HW register layout: IP-block match, not

   m5441x-address-verified from Linux; base now confirmed by NetBurner)

**No Linux driver in this tree targets the MCF5441x's DTIM instances.**
`arch/m68k/coldfire/dma_timer.c` is only built for `CONFIG_M523x`
(`arch/m68k/coldfire/Makefile:22`), and its register offsets are relative to
`MCF_IPSBAR + DMA_TIMER_n` where `DMA_TIMER_0..3 = 0x00, 0x40, 0x80, 0xC0`
(`dma_timer.c:22-25`) -- a 0x40-byte stride, not the MCF5441x's 0x4000-byte
per-timer stride already documented in `emu/dtim.py` from MCF5441XRM.pdf
ch. 39. So *this Linux commit alone* is corroboration of the *same
DMA-timer IP block's* register layout and bit encoding on a sibling
ColdFire part, not a Linux-verified MCF5441x base address -- that base
address is **not** established by anything in this section, and the earlier
version of this document overstated it by listing the base as a plain fact
in the shared JSON contract without that caveat.

The MCF5441x-specific base address (`0xFC07_0000`, 0x4000-byte stride) *is*
now independently confirmed, but by the NetBurner NNDK's `sim5441x.h`, not
by this Linux commit -- see `docs/refs/netburner-mcf5441x-layout.md` section
3. The contract file (`docs/contracts/mcf5441x-reference-v1.json`) records
that base with `"base_source": "netburner"`, distinct from the vector and
register-offset facts below that do come from this commit.

What it does confirm (HW, offsets identical across the IP block regardless
of stride):

    +0x00 DTMR   +0x02 DTXMR   +0x03 DTER   +0x04 DTRR   +0x08 DTCR   +0x0C DTCN

matching `emu/dtim.py:59-65` (`DTMR, DTXMR, DTER, DTRR, DTCN = 0x00, 0x02,
0x03, 0x04, 0x0C`; note `emu/dtim.py` does not define a `DTCR` constant --
it is unused).

CLK field encoding (HW, QUIRK-adjacent in that it is easy to get the bit
positions wrong): `dma_timer.c:34-36`

    DMA_DTMR_CLK_DIV_1  = 1 << 1   (bits [2:1] = 01)
    DMA_DTMR_CLK_DIV_16 = 2 << 1   (bits [2:1] = 10)

matches `emu/dtim.py`'s `period()` (`clk = (dtmr >> 1) & 0x03; div = 1 if
clk == 1 else 16`) exactly, including which of the two non-stop, non-external
encodings selects bus/1 vs bus/16.

Clock domain (HW): `DMA_FREQ = (MCF_CLK / 2) / 16 = MCF_BUSCLK / 16`
(`dma_timer.c:31`), confirming the emulator's assumption that CLK=10b
divides the *bus* clock (`F_BUS` from `emu/pit.py`, shared by `emu/dtim.py`)
by 16, not the core clock.

`dtrr + 1` (HW): not stated as an explicit "+1" anywhere in this Linux
tree -- `dma_timer.c` runs DTIM0 in free-run mode with `DTRR0 = 0`, which
does not exercise the reload-count arithmetic at all. The "+1" convention in
`emu/dtim.py:212-214` (`ticks = (dtrr + 1) * ...`) is carried over from RM
table 39-2 and from the identical convention `Pits.period` already uses for
PMR; this commit neither confirms nor contradicts it. Recorded here as an
open question rather than a confirmed match. The NetBurner cross-check in
`docs/refs/netburner-mcf5441x-layout.md` section 3 does not close this
gap either -- that corpus is headers only, with no `.c` file exercising
`trr`. Still open across both sources.

Vectors (HW, confirmed by the shared interrupt map even though no MCF5441x
DTIM driver exists): `arch/m68k/include/asm/m5441xsim.h:63-66`
(`MCFINT0_TIMER0..3 = 32..35`) gives vectors 64+32..35 = 96..99, matching
`emu/dtim.py:69` (`VECTORS = (96, 97, 98, 99)`).

## 4. UART8/UART9 (HW, confirmed match)

`arch/m68k/include/asm/m5441xsim.h:161-171,188-193`:

    MCFUART_BASE8 = 0xec070000   MCFINT1_UART8 = 52
    MCFUART_BASE9 = 0xec074000   MCFINT1_UART9 = 53
    MCF_IRQ_UART8 = MCFINT1_VECBASE(128) + 52 = 180
    MCF_IRQ_UART9 = MCFINT1_VECBASE(128) + 53 = 181

`emu/boot.py:34-35` and `emu/console.py`'s `USR8`/`UDR8` use base
`0xEC070000` (`UART8_USR = base+4`, `UART8_DAT = base+0xC`), consistent with
UART8's base. UART9 is not modeled anywhere in `emu/`; the contract records
its base/source/vector as a fact for future use, not as something exercised
today. Note: `TX_VECTOR = 155` in `emu/edma.py:23` is the *eDMA channel 35
completion* vector, unrelated to UART8's own INTC1-source-52 vector 180 --
distinct vectors for distinct events, not a discrepancy.

## 5. GPIO (HW, confirmed match)

`arch/m68k/include/asm/m5441xsim.h:236-268`:

    GPIO base = 0xec094000
    PODR_A=+0x00  PDDR_A=+0x0C  PPDSDR_A=+0x18  PCLRR_A=+0x24
    port stride 1 byte, order A,B,C,D,...  (C = +2, D = +3)
    MCFGPIO_SETR = PPDSDR_A  (write 1 sets)
    MCFGPIO_CLRR = PCLRR_A   (write 0 clears)

Matches `emu/gpio.py:39-47` exactly: `GPIO = 0xEC094000`, `PODR, PDDR,
PPDSDR, PCLRR = GPIO, GPIO+0x0C, GPIO+0x18, GPIO+0x24`, `PORT_C, PORT_D = 2,
3`, and the set/clear polarity used by `SdGate.on_set`/`on_clear`.

## 6. eSDHC (HW/QUIRK, drivers/mmc/host/sdhci-esdhc-mcf.c; POLICY noted

   separately)

Base (HW): `arch/m68k/include/asm/m5441xsim.h:299-303` --
`MCFSDHC_BASE = 0xfc0cc000`, matching `emu/esdhc.py`'s `BASE`.

**Mismatch, informational only (unused constant):** `MCFSDHC_SIZE = 256`
(0x100) and `arch/m68k/coldfire/device.c:565-566` maps exactly
`[BASE, BASE+0x100)`. `emu/esdhc.py`'s `SIZE = 0x1000` (4 KB) and its module
docstring's "16 KB" are both larger than what Linux (and the standard SDHCI
register file, which ends at `HOSTVER` = offset 0xFC) actually uses. `SIZE`
is not referenced anywhere else in `emu/` (grep confirms), so this is inert
-- recorded here, not changed, per this task's scope (no code exercises the
constant).

**Combined TRANSFER_MODE/COMMAND write (QUIRK, confirms current firmware's
32-bit XFERTYP model):** `esdhc_mcf_writew_be`
(`drivers/mmc/host/sdhci-esdhc-mcf.c:97-114`) intercepts a
`SDHCI_TRANSFER_MODE`/`SDHCI_COMMAND` pair and issues a single
`mcf_write32(val << 16 | mode, ...SDHCI_TRANSFER_MODE)`, i.e. one 32-bit
register at offset 0x0C holds transfer-mode flags in the low 16 bits and the
command word in the high 16 bits. The command index occupies bits [13:8] of
the 16-bit `SDHCI_COMMAND` value (standard SDHCI layout), which lands at
bits [29:24] of the combined 32-bit word. This is exactly
`emu/esdhc.py`'s `idx = (xfer >> 24) & 0x3F` against its single `XFERTYP`
register at offset `0x0C`. **This is the real hardware register, not a
Linux workaround** -- the "combined write" in the driver exists only because
generic SDHCI code models TRANSFER_MODE/COMMAND as two 16-bit registers;
the MCF5441x eSDHC only has the one 32-bit `XFERTYP`. Confirms the current
firmware's direct 32-bit XFERTYP path is the actual hardware interface, not
a shortcut around missing modelling.

**Byte/word lane XOR (HW QUIRK, not currently exercised by this firmware's
model):** `esdhc_mcf_readb_be`/`esdhc_mcf_readw_be`
(`sdhci-esdhc-mcf.c:129-158`) read `reg ^ 0x3` for a byte and `reg ^ 0x2`
for a halfword, i.e. the eSDHC register file is natively little-endian
internally and exposed on the ColdFire's big-endian bus, so sub-word
accesses need their address lane XORed against the word boundary. `emu/esdhc.py`
only ever does 32-bit register access (`_get`/`_put` use `'>I'`), so this
quirk has no observed effect on current firmware traffic. See "Deferred" below.

**Vendor DMA-error bit 28 (HW QUIRK, deferred -- not applicable to current
firmware):** `ESDHC_INT_VENDOR_SPEC_DMA_ERR = BIT(28)`
(`sdhci-esdhc-mcf.c:22`) -- the MCF5441x eSDHC's own ADMA/SDMA reports a DMA
error on `IRQSTAT` bit 28, not the standard SDHCI bit 25. `emu/esdhc.py`'s
docstring already states the firmware never sets `XFERTYP[DMAEN]` and never
touches `DSADDR`/`ADMASAR` -- bulk data moves through the SoC's eDMA
instead, bypassing the controller's own DMA engine entirely. So this bit is
real hardware behavior, but of a DMA mode this firmware does not use.
Deferred, not implemented.

**Word swap after DMA read (POLICY, not a hardware fact -- do not
implement against current firmware):** `esdhc_mcf_request_done` /
`esdhc_mcf_buffer_swap32` (`sdhci-esdhc-mcf.c:225-260`) byte-swap every
32-bit word of data *after* a `DMA_FROM_DEVICE` transfer, because "there is
no hw sdma option/flag to select the dma transfer endianness" for Linux's
own SDMA engine. This is Linux's generic MMC/SDHCI stack correcting for its
own SDMA usage; it has no bearing on the current firmware's own eDMA-driven
transfers (`SADDR = DATPORT`, a wholly different DMA path with its own
byte-order contract). Explicitly deferred per the scout handoff and this
task's scope -- not implemented, and should not be inferred as needed
without an observed firmware access proving otherwise.

## 7. ColdFire exception entry (POLICY for task-stack handling; HW for the

   frame itself)

`arch/m68k/coldfire/entry.S` and `arch/m68k/include/asm/entry.h` were
reviewed. They confirm the *hardware* frame shape ColdFire uses (format
word with vector in bits [11:2], SR, PC -- 8 bytes for a normal frame,
matching `emu/harness.py`'s `0x4000 | ((vec << 2) & 0x0FFC)` construction)
and that `rte` is the only way back. They say nothing about whether a
*handler's own* live SR should have S set and IPL raised on entry --that is
established directly from the ColdFire Programmer's Reference Manual
(already the authority `install_srtrap`'s docstring in `emu/harness.py`
cites), not from Linux. Linux's own task-stack switching, `movem` layout,
and scheduler entry/exit sequence in `entry.S` are **OS policy** specific to
Linux's kernel/user separation and are not applicable to this repo's RTOS
firmware, which has its own, already-reverse-engineered, context-switch
convention (`emu/tasks.py`, `0x40000410`). No firmware RTOS policy was
changed or informed by `entry.S`.

## Ghidra labeling

`tools/coldfire/ghidra/McfLabels.java` applies the MMIO facts above (plus the
existing eDMA base from `emu/edma.py`) as labels in a dedicated
`MCF5441X_MMIO` namespace, so they show up in Ghidra's listing without
overwriting anything a user has named. Run it against the existing `dt2`
project:

```sh
tools/coldfire/ghidra.sh run McfLabels.java /tmp/mcf-labels.log
```

It creates the necessary uninitialized memory blocks for the peripheral
regions (they fall well outside the imported MAIN OS image's mapped range)
before placing labels, and is idempotent: rerunning does not duplicate
labels or touch a differently-sourced symbol already at that address.
