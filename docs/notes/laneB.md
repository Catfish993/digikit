## Helper calls inside kernels: read-only sync analysis and a stub (base f0a3180, 2026-10-07)
Sync around one helper call, with the current ctx/St layout. Registers: a CFG kernel keeps registers in kernel variables and reads them from St at entry (`Op::St32`), writes them back at exit (`StSt32`, `direct`); every register it touches is `Req::Known`, so the known masks in St are already full. A helper needs only `StSt32` of the registers the instruction reads (that the kernel may have changed) and `Op::St32` of the ones it writes: 3 stores + 2 loads for a `3a` transfer. Flags: kept lazily as writer kinds and sources in pseudo variables, replayed into ASTATX at exit (`apply_groups`, `apply_cacc`). A flag-neutral instruction (transfers, moves, modifies, always-executed) needs nothing; one that reads or writes flags needs the pending writers applied to ASTATX before and the kernel's writer state reset (and ASTATX bits re-read, guarded known) after: about 6-10 ns more. Loop counters, PC stack, pending branches and delay slots stay in the kernel (the loop-back is lowered after the node); the interpreter's sequencer inside `exec_insn` must not see them, so the stub runs the step at a PC no loop ends at (`STEP_PC`) and puts back `pc_sw`, `icount`, `steps` (the kernel counts the instruction in its block counter and the budget). Windows: the helper goes through `Mem` (page table, dirty and watch marks), coherent with the window pointers (same page data); a store to a code page must be followed by a `dec_gen` check (not in the stub). Traps: the helper returns a status, a `Guard` leaves before the instruction and the interpreter redoes it. Call: Cranelift `call_indirect` of an absolute address (2 args, 1 result; live variables in callee-saved registers); wasm an imported call (2.7 ns) into the same instance, where St is in the same linear memory. Measured: `helper_exec` itself (call, record lookup, save and restore of three words) plus the St traffic is about 5 ns; the remaining 135 ns of a 140 ns helper is `exec_insn` (sample: 96% of helper_exec's inclusive time; the generated 3a handler, `_compute_simd` and the register-file snapshot memmove). So the sync is close to 5 ns, not to the 100 ns of a full exit; the body is what costs.
Stub (`SHARC_FAST_HELPER=1` all, or `=LO-HI` hex range; code: fast/helper.rs, lower/helper.rs, `Op::Helper`, `Node::helper`, `cfg::helper_ok`): one refusal class, the unconditional `3a` DM/PM transfer of an R register (`DM(I0,M5) = R8`, also the loads of the same loop) whose address has no static range or would use a guarded dynamic window. The lowering marks the instruction as a helper node (region.rs: a denied `3a` becomes a helper, not a stop) and the region goes on after it. Loop kernels (`build_loop`) refuse the dynamic window for these so that the CFG build takes over (the helper lives in CFG kernels only). In 0x1c8ef1 (range 1c8ef1-1c9b73) the hot loop 0x1c9b0d..0x1c9b2d now runs as one call per DO (30 iterations, 303 insns, 2 helper calls per iteration) instead of 2 calls + 2 interpreted insns per iteration.
Measured (trig1-taps 1.5 s, static-blocks+follow+gen, unlocked, A B A): base 8.899 / 8.919 / 8.904 DSP CPU s per audio s, helper range 8.772 / 8.762 (-1.5%); region calls 16.95M -> 15.48M per audio s (-1.47M), interpreted insns 8.96% -> 8.66% (-1.48M insns/s), helper calls 1.49M per audio s; PCM 3bf3ba3026953c22 in all runs. 0x1c8ef1's estimated cost 1201 -> 656 ms per audio s by the model. Implied: a region call (130 ns by profile) plus an interpreted insn (105) = 235 ns replaced by a 140 ns helper: 95 ns saved per helper instruction. Blanket helpers (all `3a` in the firmware) are worse: +0.30 s (9.2 vs 8.9), 3.7M helper calls per audio s: the guarded dynamic-window accesses that hit natively cost 1 ns and became 140 ns.
Estimate for the general case with the interpreter step as the body: runs of k interpreted insns between regions gain 130 - 35k ns (helper 140 against interpreted 105): 17M calls saved against 45M interpreted insns slowed gives about +0.6 s of 8.9 (7%). With a body of 30 ns (a generated form handler without Engine::step, snapshot memmove or decode) the same count gives about 5 s (calls 2.2 s + 45M x 75 ns = 3.4 s): the helper body, not the sync, decides.
