# Digi emulator handover — 2026-09-11

Replaces the earlier 2026-09-11 draft, which was wrong in its central claim.
That draft said the priority-6 Main OS task never ran and blamed the
scheduler. The task ran the whole time; it was being starved. Do not act on
the previous version.

## Current state

**Digitakt II 1.15C boots to Main OS and renders correctly.**

```bash
uv run python -m emu.run Digitakt_II_OS1.15C.syx --slc
```

Reaches the sample page (project name, BPM, TUNE/PLAY/SAMP, LEV/STRT/LEN/LOOP)
and stays stable. Representative steady state:

```text
source panel   lit 1900   frame 300   2.6 / 15.0 fps (17% of real time)
PIT0 1724  PIT2 1911  PIT3 144  DTIM3 919  mainloop 921  jobs 1  tasks 6
pc 0x40002a18  task 0x4094eee8  221.3M instructions
```

The display handover happens at roughly 80M instructions, where PIT3 goes
0 -> 15 and mainloop 0 -> 73 in a single reporting step.

**Digitone II 1.10E reaches Main OS but on a fallback display path.**

```bash
uv run python -m emu.run Digitone_II_OS1.10E.syx --slc
```

Renders the synth interface (SYN 1, TUN1/WAV1/PD1/LEV1, TUN2/WAV2/PD2/LEV2).
Representative steady state:

```text
source panel   lit 1843   frame 228   2.1 / 15.0 fps (14% of real time)
PIT0 957  PIT2 1116  PIT3 0  DTIM3 472  mainloop 477  jobs 1  tasks 4
pc 0x40000410  task 0x405831cc  154.3M instructions
```

`PIT3 0` is the tell. `display_start` is the code that arms PIT3 (it writes
`0x4323` to `0xFC08C002` then `0x93F` to `0xFC08C000`; PIT3's base is
`0xFC08C000`). PIT3 never firing means **`display_start` never ran**, so the
display module never took over vector 208 — vector 208 still holds the intro
ISR `0x400d4fb8`. The panel composes and DTIM3 paces it, so it looks right
and is not. This is the open bug.

Do not describe Digitone as working. The supported claim is "renders Main OS
through a fallback path; the display module never initialises."

### The stall fix (14ab93a)

`unblock` force-satisfies pended semaphores so boot never blocks on hardware
that will never answer, exempting pend sites that re-check and loop. The RTOS
tick dispatcher's wait was missing from that list and fails differently: its
loop is

```text
pend_b(tick_sem); mutex_lock(m); run every due callback; mutex_unlock(m)
```

so the wait *is* the pacing. Satisfying it made a tick-paced loop
free-running; the 54-slot software timer wheel then ran ~100x per real tick,
consumed half of all post-intro instructions, and starved the priority-6 Main
OS task. Measured on a boot280M resume, 250M post-intro instructions:

```text
force-satisfied pends   137,061 -> 175
mainloop entries              0 -> 1,462
DTIM3 fires                   0 -> 1,491
tasks created                 0 -> 4
distinct tasks scheduled      2 -> 6
```

Two independent arms were bit-identical.

`tick_dispatch` is a 36-byte signature at `0x40002a46`, occurring exactly once
in each image and byte-identical at that address in both builds. Digitakt's
own boot log confirms the semantics, creating a priority-10 task at that
entry. `tick_pend` is `tick_dispatch + 0x2a`, the return address of the
`jsr (a4)` two bytes earlier. Build-specific operands resolve per image:
Digitone sem `0x46488008` / mutex `0x464880d0`; Digitakt `0x47d9ade0` /
`0x47d9aea8`.

### The flicker fix (5a00be5)

`_publish_panel` read FRONT once per BUDGET at an arbitrary point.
`emu/panel.py` documents why that is wrong: the diff walks pages 0..7, so a
mid-flush read is torn, and after the swap FRONT is the buffer being rendered
into *next*. Frames are now latched at `panel_diff` entry, the one moment
panel.py guarantees FRONT is complete. Measured over 400M instructions on
Digitakt boot400M, comparing both sampling points in the same run, counting a
frame as torn below 75% of median lit pixels:

```text
arbitrary read   331 frames  median 1900 lit  min  121  torn 43 (13.0%)
latched at diff  326 frames  median 1900 lit  min 1895  torn  0 ( 0.0%)
```

### Fault visibility (5325873)

`Machine._fault` mapped a zero page and resumed, so every access to unmodeled
hardware was silently absorbed. It now records page, faulting address, first
PC and access kind before mapping. Runtime behaviour is unchanged. Read it
with `m.fault_report()`.

Cold boot reports 104 pages on Digitone and 129 on Digitakt. Most are benign
SDRAM sizing. The ones that are not:

```text
0xEC09000E  read   from 0x40000524   peripheral, no model
0xFC04002D  write  from 0x40000500   peripheral, no model
0x00000000  read   from 0x400d116a   null dereference
0x80000000  write  from 0x4000046E
0x8C000006  write  from 0x400d1984
```

A snapshot resume reports zero faults, because restore pre-maps every page the
earlier boot touched. Cold boot is the only place this is informative.

## The open Digitone bug

Chain traced to the top, nothing fixed:

```text
FUN_400d1110 (early boot)  --calls-->  FUN_4011d67a  (SD / eSDHC bring-up)
                                            | clears 0x44459024 at 0x4011d694
                                            | sets it at 0x4011dbdc, only after
                                            | the full init sequence completes
                                            v
FUN_4011dcb4:  return 0x44459024 != 0  --gates-->  structure init
                                            v
FUN_4011ee0c:  zeroes flag at +0x1de6c, only initialises under that gate
                                            v
FUN_4011ecac:  reads flag at +0x1de6c  --gates-->  returns 0 / 1 / 2
                                            v
prio-6 task at 0x4002e6b2:  needs 1, gets 0, diverts to 0x4002f488
                                            v
                          display_start skipped, PIT3 never armed
```

The prio-6 gate, at `0x4002e6b2`:

```text
4002e6b2  jsr $4011ecac      ; status -> d0
4002e6bc  cmp.l d0,d1        ; d1 = 1
4002e6be  beq.b $4002e6ce    ; status == 1 -> proceed to display_start
4002e6c0  move.l $4026e1e0,d5
4002e6c6  btst.b #4,d5       ; bit 4 is an override
4002e6ca  beq.w $4002f488    ; taken -> divert past display_start
4002e6fc  jsr $401233f2      ; display_start (never reached)
```

`FUN_4011ecac` decompiles to:

```c
if (*(char *)(param_1 + 0x1de6c) == '\0') return 0;
return -(*(int *)(param_1 + 0x1de70) != 0xBEEFBACE) + 2;
```

`param_1` is a lazy singleton from `FUN_40179c26`, a 0x1e04c-byte allocation
constructed by `FUN_4011ee0c`. At runtime it was `0x445a7ef0`, putting the
flag at `0x445c5d5c` and the magic at `0x445c5d60`.

Measured facts, boot280M resume, 200M post-intro instructions, both with
`esdhc=False` and `esdhc=True`:

```text
0x44459024 (gate flag)          0
FUN_4011d67a  (SD bring-up)     0 hits  -- never called
FUN_4011dcb4  (gate read)       1 hit
FUN_4011ecac  (validity)        1 hit
display_start                   0 hits
PIT3 fired                      0
vector 208                      0x400d4fb8 (still intro ISR)
```

`esdhc=True` changes `0xFC0CC024` (eSDHC PRSSTAT) from `0` to `0xFF900038` and
changes nothing else, because the bring-up never runs. The existing `Esdhc`
model is not the missing piece.

`FUN_4011d67a` itself configures GPIO (`0xEC09404E`, `0xEC094050`,
`0xEC094054`, `0xEC09404D`; GPIO base is `0xEC094000`) and then polls
`0xFC0CC024 & 3` — eSDHC PRSSTAT command-inhibit bits. Ghidra marks most of
the function unreachable because it cannot prove that loop exits, so the
decompilation past that point is not trustworthy; read the disassembly.

**The next experiment** is a cold boot with hooks on `FUN_4011d67a` entry and
on `0x4011dbdc`, to settle whether it ran and failed before the snapshot was
taken or never ran at all. The resume path cannot answer this, because the
snapshot already contains whatever happened.

`0x4026e1e0` in the Digitone image is `0x00000000`, so the bit-4 override is
clear. Whether anything is supposed to set it at runtime is unknown.

## Disproved — do not re-investigate

Each of these was tested and is dead. Re-running them wastes a session.

- **SR save/restore corrupting condition codes.** A snapshot-style
  `reg_read`/`reg_write` round-trip preserves Z in both directions and the
  following conditional branch is correct. Not a source of divergence.
- **A mutex deadlock at `0x40001622`.** That address is
  `move.l (A0),(0x4,A2)`, the uncontended acquire fast path in `mutex_lock`
  (`FUN_40001608`). It never blocks. It was simply where the instruction
  budget stopped.
- **The heap-allocator mutex `0x4441f7e8` being held.** Observed free at the
  stall: owner 0, no waiters.
- **A memcpy with a corrupted length.** The block-copy routine at
  `0x40125f18` was called zero times in the stalled window. A task parked at
  `0x40125f46` is preempted mid-copy, which is normal.
- **The priority-6 Main OS task being absent, unscheduled, or blocked.** It is
  created (`task_create(0x405831cc, 0x4002e688, 6, ...)` from `FUN_4002e224`),
  entered, and runs continuously.
- **The direct handler-SR write from `84b4151`.** Ruled out by a controlled
  A/B in the previous session. Do not revert it.

Also wrong, from a subagent, and refuted by reading the raw image: a claim
that the prio-6 entry `0x4002e688` is zero-filled. It begins `4e56ff58`
(`link a6,#-0xa8`), a normal prologue.

## Tooling

### Boot verdict

```bash
uv run python tools/bootcheck.py \
  --syx Digitone_II_OS1.10E.syx \
  --snapshot snapshots/Digitone_II_OS1.10E/boot280M.snap \
  --post-intro 120000000 --verify --json out.json
```

Emits `PRE_INTRO | POST_INTRO_STALL | PARTIAL_MAIN_OS | MAIN_OS_RUNNING |
CRASHED` with reasons and a state digest. `--verify` runs two independent arms
and requires their digests to agree. Exits non-zero unless
`MAIN_OS_RUNNING`. Device-agnostic via the resolved profile, but so far only
exercised against Digitone snapshots.

`--profile` adds a basic-block profile and is **off by default on purpose**;
see Guardrails.

### Static analysis

The Ghidra project `~/ghidra-projects/dt2` now holds **two** programs:

```text
/section_3_MAIN_OS.bin   Digitakt II 1.15C   md5 f37932dc16f2f03e1d2c263bc46950c4
/dn2_MAIN_OS.bin         Digitone II 1.10E   md5 98fd9df8dd3f0d3b6d1305b0e9bd9823
```

Until today it held only the Digitakt image, so any earlier static analysis of
a Digitone address was reading unrelated code. Always name the program.

```bash
export GHIDRA_INSTALL_DIR=/opt/homebrew/Cellar/ghidra/12.1.3/libexec
uv run python tools/decompile.py dn2_MAIN_OS.bin 0x4011ecac    # ~2.6s
uv run python tools/export-profile.py ...                      # profile -> JSON
uv run python tools/apply-profile.py ...                       # JSON -> Ghidra labels
```

`tools/ghidra.sh` still hardcodes the Digitakt program; prefer the PyGhidra
tools above. PyGhidra 3.1.0 is installed in the venv from the Ghidra install's
own bundled wheels, via `uv pip install` — it is **not** in `pyproject.toml`,
so `uv sync` will not restore it.

Note `tools/` shadows PyGhidra's `ghidra` namespace; both PyGhidra tools strip
their own directory from `sys.path` before importing. Keep that if you write
another.

Profile resolution: 44/44 symbols on Digitakt, 42/44 on Digitone (the two
misses, `transport` and `call_sites`, are already documented in
`emu/symbols.py` as not resolving there).

## Guardrails

Carried forward from the previous handover, still in force:

- Evidence before emulation behaviour; do not invent registers or magic
  return values.
- Preserve checkpoint and firmware hash/manifest checks.
- Production execution may be subdivided only at timer deadlines.
- Do not use TB flushing, `srtrap`, weak-pointer bypasses, or branch forcing
  as production fixes.
- Do not read lazy CCR/SR from an asymmetric Python code hook and treat it as
  authoritative.
- Keep firmware-derived checkpoints/traces and native debug builds under
  `/tmp` or ignored paths.
- Do not commit the scraped NetBurner corpus or unrelated/proprietary files
  without an explicit provenance/licensing decision. Untracked material that
  must stay untouched: `Syntakt OS 1.40A/`, `docs/HANDOVER-2026-09-09.md`,
  `docs/refs/netburner-coldfire/`,
  `docs/refs/dspi2-edma-blocker-and-register-sources.md`, `foo/`, `maybe.md`,
  `scratch/`, `tools/nbdocs-scrape.py`.

Learned today, and worth as much as the rest:

- **`UC_HOOK_BLOCK` changes outcomes, not just timing.** The same boot280M
  resume reached the Main OS message loop with the block profiler off and did
  not with it on. Use it to find a hot loop; never to decide pass/fail. This
  is why `bootcheck --profile` is opt-in.
- **Never compare an address across builds.** Every application address
  differs per image. Reading a Digitone-derived address in the Digitakt image
  produces confident nonsense. Resolve through `emu/symbols.py`.
- **A snapshot resume hides anything that happened before it.** Zero fault
  pages and an unreachable init function on a resume mean nothing; cold boot.
- **Verify subagent findings against the raw image.** Two claims today were
  confidently wrong and cheap to disprove.

## Protecting Digitakt while fixing Digitone

Digitakt is the tested build and currently the only one on the correct display
path. Any Digitone change must not regress it.

Before and after any change:

```bash
uv run python -m emu.unicorn_compat          # "compatible": true
uv run python -m unittest discover -s tests -q   # 59 tests, 5 skips
uv run python -m compileall -q emu tools
uv run python -m emu.run Digitakt_II_OS1.15C.syx --slc
```

The Digitakt run must still reach the sample page with `source panel`,
non-zero `PIT3`, `tasks 6`, and a `panel` lit count that stays near 1900
without dipping to a fraction of it. A bounded headless Digitakt cold boot
(`emu.dspboot.run(..., limit=80_000_000, machine_out=...)`) is a faster smoke
test: it completes without error and its `TASK_CREATE` log includes the
priority-10 tick dispatcher at entry `0x40002a46`, which is the symbol the
tick fix depends on.

Prefer changes that resolve per image through `emu/symbols.py` over anything
keyed to a hardcoded address, which is what let the tick dispatcher fix apply
to both builds from one signature.
