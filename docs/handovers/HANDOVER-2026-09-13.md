# Digi emulator handover — 2026-09-13

Supersedes nothing in `HANDOVER-2026-09-12.md` except its work-item 1, which
is now done. Read the Dead ends section before re-deriving anything here.

## The front panel works

You can press buttons and turn encoders on both builds, and the firmware
responds. That was work item 1 and it is finished.

`emu/panelin.py`:

```python
press(m, profile, channel, bit, held=0)
release(m, profile, channel, bit, held=0)
buttons(m, profile, channel, mask)      # whole 8-button group state
encoder(m, profile, channel, delta)     # signed detents
state(m, profile)
```

Verified on Digitone: `encoder(m, profile, 0, +1)` replaces the on-screen
`TUN1` label with its live value `0.00`, and pressing channel 0 bits 0..5
selects the TRIG / SYN / FLTR / AMP / FX / LFO pages -- the real page-button
row, in physical order.

## The panel is not memory-mapped

This is the thing that cost the most to establish, so do not re-derive it.
`tools/mmiotrace.py` (new) profiles MMIO by *recurrence* rather than total,
chopping a run into fixed instruction-count windows so a scan loop is
distinguishable from an init burst. Over 60M post-intro instructions on each
build it finds **zero GPIO, zero DSPI, zero unclaimed addresses** -- only
timers and the UART8 transmit DMA. Nothing scans a key matrix.

Also ruled out: all six FlexBus chip-selects read zero, and the only non-RAM
regions ever mapped are `0x80000000` (boot ROM) and `0x8C000000` (the DSP).
The panel is not on an external bus either.

A separate microcontroller does the scanning and talks over **UART8** at
156250 baud (5x MIDI rate). Events arrive by eDMA channel 34 into a
1024-byte ring, then vector 154.

**UART8 is not MIDI, and not a text console on the wire.** Both claims exist
in older docs and both mislead. MIDI DIN is **UART9** at 31250 baud (verified:
`pea #0x7A12` into the UART9 init), entirely unmodelled. The `#HELLO` console
is real but is a software dispatcher that `emu/serial.py` reaches by injecting
into its queue, bypassing the wire.

## The wire protocol

    header = (tag << 4) | channel

    tag 0x2   1 byte    buttons -- an 8-bit STATE BITMASK for that channel's
                        eight buttons. The firmware XORs against the previous
                        byte and derives edges itself; there is no release
                        message on the wire.
    tag 0x3   1 byte    encoders -- a SIGNED delta. Not gray code, not
                        separate inc/dec messages.
    tag 0x7   8 bytes   a block the console task consumes; not input.

Any other tag is parsed and discarded. No length field, no checksum.

The parser is byte-identical in both builds; only data addresses move. So
`emu/symbols.py` gained five symbols chained off one Fixed anchor:
`uart8_init` is BSP-layer code at the same address in both images, the
`clr.l` operand at +0x18 is the driver's globals base, and the field offsets
inside that block are identical (+0x10 ring, +0x30 consume index, +0x40
receive callback). That is also the fix for `emu/serial.py`, which hardcoded
Digitakt's and on Digitone read `0xFFFFFFFF`.

## Reading events instead of the screen

`tools/panelsweep.py` (new) maps the whole panel by hooking `queue_send` and
decoding the 16-byte event record the firmware itself emits:

    +0x00  type   0 = button, 1 = encoder
    +0x07  control code
    +0x08  encoder value (signed delta)   -- note: union-like layout,
    +0x0B  button flags (0x01 press, 0x10 release)
    +0x0C  timestamp

**Do this instead of diffing the framebuffer.** The record is the firmware's
own output, so it is immune to render timing, modal state and frame tearing.
Framebuffer diffing cost hours and produced two contradictory maps; the
record method mapped all of Digitone in 85 seconds.

`queue_send` (`0x40001896`) is the only literal address the tool uses, and it
is genuinely identical in both builds. Callers and the sink queue are
discovered at runtime by record shape plus a settle-built ignore-set, so the
tool is build-agnostic.

### The maps

Buttons, both builds: `code = channel * 8 + bit + 1` for channels 0..5
(codes 1..48). Channel 6 breaks the pattern in both, and differs between them:

| ch6 bit | Digitone | Digitakt |
|---|---|---|
| 0 | 50 | 50 |
| 1 | 49 | 49 |
| 2 | 0 (unassigned) | 100 *(tentative)* |
| 3 | 0 (unassigned) | 116 *(tentative)* |
| 4..7 | 51, 52, 53, 54 | 100, 101, 112, 111 *(tentative)* |

Digitakt fills the two slots Digitone leaves empty. Digitakt's ch6 bits 2..7
are **tentative**: that build defers some records until the next panel event,
and the reassembly pass is only reliable where a code formula exists to check
against. Bits 0..1 are clean on both.

Encoders, both builds: `code = channel + 1` for channels 0..8 -- eight data
encoders plus level. Signed delta verified at +1, +5 and -1.

### The names come from the firmware

The factory test mode carries `char *` tables of control names indexed by
control code, terminated by `0xFFFFFFFF`. That is the firmware telling us
what each code means, not us inferring it from what the screen did, and it
was found statically -- no emulator time at all.

They resolve through `emu/symbols.py` as `panel_button_names` and
`panel_encoder_names`, so they are read out of the image at run time rather
than written down per build: `emu/panelin.py`'s `control_name(m, profile,
code)` and `control_names(m, profile)` return them. Verified to resolve to
Digitakt `0x401f7c90` / `0x401f7c1c` and Digitone `0x401de25c` / `0x401de1e8`,
cross-checked by hand against the raw images.

Buttons, identical on both builds through code 50:

    0 UNDEFINED   1 TRIG      2 SRC       3 FLTR      4 AMP
    5 FX          6 MOD       7 PRESET    8 SETTINGS  9 TEMPO
   10 YES        11 UP       12 NO       13 LEFT     14 DOWN
   15 RIGHT      16 TRK      17 FUNC     18 KEYBOARD 19 RECORD
   20 PLAY       21 STOP     22 PAGE     23 PTN      24 SONG
   25..40 TRIG 1 .. TRIG 16
   41..48 ENCODER A .. ENCODER H   (the encoder PUSH buttons)
   49 LEVEL

Then they diverge, which is the whole reason the tables are resolved rather
than hardcoded:

    Digitakt  50 SAMPLING, table ends
    Digitone  50 VOICE  51 ARP  52 PLUS  53 STACK  54 MINUS

Encoder ROTATION is a separate code space (table 2), both builds:
`0 UNDEFINED, 1..8 ENCODER A..H, 9 ENCODER LEVEL`.

Two notes. The page-button names here are the test mode's internal labels:
code 2 is `SRC` and code 6 is `MOD`, while Digitone's normal-mode UI captions
them `SYN` and `LFO`. Same button, different layer. And this explains the
tentative Digitakt channel-6 readings -- Digitakt's table simply ends at 50,
so bits 2..7 of channel 6 have nothing to report and the measured values
there were junk.

## Dead ends -- do not repeat these

- **DTCN is not the problem.** The encoder handler reads DTIM0's counter at
  `0xFC07000C`, which reads 0 forever. That is *hardware-faithful*: DTMR0 is
  `0x0000` (stopped, held in reset) at every sample, and nothing in the whole
  image ever writes it. DTCN is a payload timestamp field only -- never a
  gate, divisor or scale. Implementing a free-running DTCN would be inventing
  hardware and would fix nothing.
- **The `< 0x28` debounce gate is not the problem.** It compares a *software*
  tick counter (`0x464b2bb0` on Digitone, incremented by the periodic flush)
  against a per-index stamp array. Measured: 9/9 accepts, 0 discards.
- **Encoders were never broken.** Both dead ends above were chased because
  encoders looked dead. They were not: the observation window was too short
  for the consumer task to be scheduled, so even a known-working *button*
  showed no change in the same run. Read the event record, not the screen.
- **A fixed instruction cap on the intro wait has burned three agents.**
  `sdboot280M.snap` has the intro LIVE at restore; handover fires at ~64-70M
  on Digitone and ~140M on Digitakt. Spin uncapped until the `intro_done`
  hook fires, then settle. Capping it early leaves the timers held and
  silently changes results.
- **MAIN OS loads at `0x40000400`, not `0x40000000`.** Addresses derived from
  a raw section-file offset with the wrong base are 0x400 too low.

## Device files

`devices/*.toml`, loaded by `emu/device.py`. One file per product, carrying
only what the image cannot tell us:

- **identity, keyed by the firmware's SHA-256.** The filename is a hint for
  error messages. `device.identify(syx)` returns `(Device, Firmware)` and
  *refuses* an unknown hash rather than guessing -- an unmapped release is a
  real answer, and picking one of two products for it is how you run a panel
  that is not the one in front of you.
- **the wire mapping.** `wire_for(code)` and `code_at(channel, bit)`.
  Channels 0..5 are linear; channel 6 is not, and differs per product, so
  each file declares its own exceptions. Every declared code round-trips.
- **display grouping**, which is editorial: pages, modes, confirm, arrows,
  modifiers, transport, select, trigs, encoder pushes, level, product.

Deliberately NOT in these files: control names and guest addresses. Names come
from the firmware's own tables and addresses from signatures, so neither can
drift out of sync with the image and neither needs a new file per firmware
release. Cross-checked: every code the device files declare has a name in the
firmware's table, on both products, with none missing.

Naming note: `profile` already meant three different things in this tree
(`symbols.Profile`, the Ghidra profiles in `tools/export-profile.py`, and
`gui.Panel`, which is the *screen*). This is a **device**, deliberately.

## The emulator was never CPU-bound. It was `count=`-bound

The GUI ran at 31% of real time and `docs/FINDINGS.md` explained why: "~2.2M
instr/sec is simply what Unicorn's m68k core does here." **That was wrong**,
and it had been steering decisions -- `docs/NEXT.md` concluded from it that
"further gains have to come from executing fewer instructions, not from
tuning the harness."

Measured this session, same machine, same hook set, same stop mechanism, the
only difference being whether `count=` is passed to `emu_start`:

    counted    2.0M instructions/sec
    uncounted 15.5M instructions/sec      7.6x

A cProfile of the running configuration puts **99.5% of wall time inside
`emu_start`** and every Python callback in this project under 0.5% combined --
so the old "every hook in this project is free" half of that finding was
right, and only the ceiling was wrong. Real time needs 4.68M instr/sec, so
uncounted leaves roughly 3x headroom.

`count=` is what makes `emu_start` stop on an exact instruction, and Unicorn
implements it by counting every instruction, which breaks TB chaining. The
`~1.8x` figure quoted in `emu/gui.py` and `emu/longrun.py` was measured on the
intro; on the settled main OS the same comparison is 7.6x. The penalty grows
with how much translated code is in play, so treat 1.8x as a floor.

### What replaced it

`longrun.spin(fast=True)` bounds each step with a block hook instead, which
leaves the fast dispatch path intact. Two costs, both real:

- A block's `size` is BYTES, not instructions, so the count is an estimate
  divided by a bytes-per-instruction ratio. That ratio is **not** a constant:
  measured on this image it moves between 3.05 and 3.79 depending on what is
  running, so `_FastStepper` re-measures it from a genuinely counted step
  every 16 steps. One counted step in sixteen costs ~6% of the tax. In
  practice the estimate tracks the counted path to about 0.03% -- the same
  deadline steps came out 156005/156005, 124795/124824, 109212/109183.
- A timer fires up to one basic block late (~8 instructions here) rather than
  on the exact instruction, so the instruction stream and the boot digest
  change.

Therefore **`fast` is opt-in and never the default**. `tools/bootcheck.py`,
the tests, and anything making a determinism or pass/fail claim keep the exact
path. Verified: with these changes in, the default path on Digitone still
gives `MAIN_OS_RUNNING`, `deterministic: true`, digest **d1e8c68377741b68** --
byte-identical to what `HANDOVER-2026-09-12.md` recorded.

The GUI opts in, and then paces itself back to real time with `INSTR_PER_SEC`,
because uncounted it outruns the hardware and a sequencer at 3x tempo is worse
than one at a third. `--exact` restores counted stepping for comparison
against bootcheck; `--unthrottled` removes the pacing.

## Known limits

- From a settled state, running past ~16-20M instructions raises an
  "INITIALIZING +DRIVE..." dialog that never clears, because the eSDHC model
  does not back bulk block reads. Keep observation windows under that.
- Page buttons behave *momentarily* -- the page reverts shortly after
  release. May be an artifact of `unblock=True` rather than real. Unresolved.
- Digitakt's `boot280M.snap` renders a blank screen post-intro, so screen-based
  identification does not work on that build. The record method does.

## What is left

1. A GUI control surface in `emu/gui.py` -- it already has the emulator
   thread and framebuffer view, so a clickable panel wired to
   `emu/device.py` + `emu/panelin.py` is an addition, not a rewrite. The
   device files already carry the grouping to draw.
2. `emu/config.py` still hardcodes `TESTED_SYX = 'Digitakt_II_OS1.15C.syx'`
   and lets it win ties between firmware files. `emu/device.identify()` now
   answers that question properly, by hash; config should defer to it.
3. The TX direction is unmodelled. It is a tagged binary stream --
   `0xB5 <index> <R> <G> <B>` is an RGB palette/LED command (136 occurrences,
   134 clean 5-byte gaps), `0xB9 <index> <value>` is 3 bytes, plus a
   10-byte-periodic table upload. Modelling it would give LED readback.
4. Then the older list: container repacking, DSP p-code semantics, the DSP
   dispatch question.
