# 36. Boot-time loading: hook point, restart, persistence, parameter identity (spike)

Spike for the boot-time design (docs/plans/digikit-runtime.md decision 9), 2026-10-17.

Static only (cfdb dumps, `tools.coldfire.fw`, refscan-style byte scans, objdump of section 3 at vma = file offset + 0x40000400). No emulator run.
Marks: **[D]** read here once, **[O]** open. Nothing here is second-agent checked, so nothing is **[V]**.
Ports: DT2 1.16, DT2 1.17, DN2 1.11, DN2 1.12. Mapping between ports by function hash (`func_hash`, strict, else loose); where the hash was not unique the address is searched by byte pattern and says so.

## 1. Boot order and the hook point

The reset entry (`0x400004e8`, takes the bootstrap's flags word from 4(sp) into `0x4029e9b0`) runs `main`, which is the boot thread below
(DT2 `FUN_400cc864`; it ends in an empty `while(true)`, so it is the idle context after it has created every task).
**[D]** Order inside the boot thread, with call-site addresses:

| step | DT2 1.16 (`FUN_400cc864`) | DT2 1.17 (`0x400cc9c8`) | DN2 1.11 (`0x400cec98`) | DN2 1.12 (`0x400cedfc`) |
|---|---|---|---|---|
| static ctors, first two tasks (`FUN_40001118`, `FUN_40002bf0`) | 0x400cc888..89e | - | 0x400ceccc, 0x400cecd2 | - |
| DSP boot: reads section 7, bit-bangs it over DSPI2 (DT2 `FUN_400ccf74`, 1.17 `0x400cd0d8`, DN2 `0x400cf34c`/`0x400cf4b0`) | 0x400ccaee | 0x400ccc52 | 0x400cef22 | 0x400cf086 |
| eMMC (ESDHC) init (`FUN_4012d43c`, `..d4b2`, `..da98`, `..dc80`) | 0x400ccb02..b1c | 0x400ccc66..c80 (`0x4012d718`..`0x4012df5c`) | 0x400cef36..ef50 (`0x4012bafc`..`0x4012c340`) | 0x400cf09a..f0b4 (`0x4012bddc`..`0x4012c620`) |
| boot record read (A/B sector `0x40000`/`0x48000`, 14.5 MB "MRAM arena" into RAM) | `FUN_400f0628` @0x400ccb6a | `0x400f078c` @0x400cccce | `0x400f2004` @0x400cef9e | `0x400f2168` @0x400cf102 |
| live project decoded from the arena container into the Project object (`0x41776c9c` on DT2) | `FUN_400c0c2c` @0x400ccbd6 | `0x400c0d90` @0x400ccd3a | `0x400bb25c` @0x400cf00a | `0x400bb3c0` @0x400cf16e |
| card mount (MmcFs, superblock sector `0x5d8000`, takes the mutex `0x46f4deb0`) | `FUN_4015a450` @0x400ccc00 | `0x4015a72c` @0x400ccd64 | none (no path filesystem) | none |
| block-frame interrupt installed (vector 191, `_DAT_80005348 = 1`, INTC1 ICR `0xfc04c07f`) | `FUN_4002dc62` -> `FUN_4002d4f2` @0x400ccc18 | same @0x400ccd7c | `0x40025dee` @0x400cf022 | `0x40025dee` @0x400cf186 |
| create the main OS (UI) task: stack `0x28000`, priority 6 | `FUN_4003324e` @0x400ccce6 | @0x400cce4a | `0x4002e8d0` @0x400cf0ea | `0x4002e8d0` @0x400cf24e |

Tasks created before the main OS task: priority-9 dispatcher, `FUN_40002bf0` worker, the intro task (`FUN_400d12e4`, prio 7), `FUN_4012d0dc`, the MIDI worker (`FUN_401206d2`), `FUN_4015394a` (prio 5).
Other tasks are created in the same thread; the exact scheduler start is not traced **[O]**, but the thread takes the eMMC mutex and blocks on semaphores before any task exists, so blocking calls work there.

Main OS task (DT2 `FUN_400337ba`, same address on 1.17; DN2 entry `0x4002ed34`, not a Ghidra function) **[D]**:
singletons (TimerManager, Brain, MmcFs) -> SLC / factory-reset / "Migrate presets" / "Update MMC Caches" background jobs (`0x4003382c`..`0x40033940`) -> view system init (`FUN_40031100` @0x40033b9e; DN2 `0x4002c7d8` @0x4002f016) -> "MAINTENANCE MODE" / "MMC NOT IN SLC MODE" confirm windows -> `FUN_4003329a`, `FUN_400d2728` @0x40033c30 -> **MainScreenView constructed** (`jsr` @0x40033cf2 DT2 1.16 and 1.17; `0x4002f16a` DN2 1.11 and 1.12) -> `FUN_400f04c8` (picks the next A/B boot-record slot) -> **event pend `jsr FUN_40001928` @0x40033d06** (DN2 `0x4002f17e`; this is where the runtime's UI-loop hook sits today) -> first UI event.

The machine view (`FUN_40060f50`, DN2 `0x4005b2c0`) is reached from the MainScreenView constructor: `path` MainScreenView ctor -> KitBrowser -> MachineSelectionView ctor (`0x400611fe`) -> `FUN_40060f50` -> `FUN_40052a08` (list getter). There is no path from the boot thread to it. **[D]** The view is therefore built after the DSP boot, after the frame interrupt exists, after mount, after the project is decoded, and before the first UI event.

Answers to (a)/(b)/(c):
- (a) Block read: `FUN_4012deda` (DT2 1.16; 1.17 `0x4012e1b6`; DN2 `0x4012c59a`, `0x4012c87a`) is used by the firmware itself in the boot thread at the "boot record read" row above, which is right after eMMC init and before mount. It takes the ESDHC mutex and waits on a semaphore. **[D]** The raw module store (sectors, not MmcFs) therefore needs no mount: the earliest legal read is just after the eMMC-init row. Mount is not a precondition on either device.
- (b) DSP: booted at the DSP-boot row; the CF-to-DSP frame needs the vector-191 interrupt, installed at the "block-frame interrupt" row, which is AFTER the project decode and mount. So DSP code (core/dsp-link) cannot be sent from any point before that row. At the main OS task it is flowing. Time to first DSP acknowledgement is not measured **[O]**; `dl_send` retries and times out after 900 blocks (0.6 s), so the boot hook should poll `dl_poll` with its own bound.
- (c) Before the machine view: the MainScreenView constructor is the first user of the tables. Before the working project: NOT possible together with (b): the project is decoded in the boot thread BEFORE the frame interrupt exists (decode row precedes the interrupt row on all four ports). The firmware's order is: DSP boot, eMMC, project record read, project decode, mount, frame interrupt, tasks, main OS task, machine view, first UI event.

Does the project decode need the registry? **[D, static]** The sound loader (`FUN_400db24e`) keeps a stored type byte by an immediate compare that `core/machines` already widens (module.toml line 524), and it does not read the machine rows. The only path from `write_live_project` (`FUN_400df7f6`) to the type-argument mapping (`FUN_400da23e`, the descriptor lookup) is the "reset one slot to a default sound" branch (`FUN_400e6378`). So a track that names type 16 loads with its type byte intact and the row is only read when the page, list or DSP selector is used. Residual risk **[O]**: other derived values at load (SoundParameterSet / `Sound::updateMirror` on first access) were not traced for reserved types.

**Recommendation: one late point, the main OS task, immediately before the MainScreenView constructor call** (DT2 1.16/1.17 `0x40033cf2`; DN2 1.11/1.12 `0x4002f16a`; the call is `jsr abs.l`, the same retarget style as the existing hook). There:
1. block reads work (mutex, scheduler running), 2. the DSP and the frame interrupt are up, 3. the registry rows are written before `FUN_40060f50` runs, so the stock builder includes the module machines (the reserved rows are already in the static list; `dynreg_copy` filters on a non-empty name) and neither the view hook nor a second builder call is needed at boot, 4. the project is already loaded, but that is harmless (above).
Order inside the hook: read selection -> arena + registry rows + CF code -> `dl_send` for each DSP module and wait for DONE (bounded). DN2 is slow (71.6 KB/s: 64 KiB is about 1 s; 4 KiB about 0.1 s); if a DN2 boot delay is not wanted, put the DSP upload into the first pass of the existing UI-loop hook and keep rows + CF code at the boot point. Until the upload is DONE a saved track on a module machine would play with the selector of type 0 for that time **[O]** (not measured).
Fallback if the registry rows are needed before the project decode: the call at DT2 `0x400ccbd6` (`jsr FUN_400c0c2c`; 1.17 `0x400ccd3a`; DN2 `0x400cf00a`, `0x400cf16e`) is the last point with a legal block read and a stock project not yet decoded; rows and CF code only, DSP code must wait for the late point. Not recommended: two hooks, no known need.

## 2. Unsaved working state

**[D]** There are three stores, none periodic:
1. Explicit saves: project slots in the MmcFs pool (slot 0 at `0x58000`; save writes exactly that slot, finding 25), pattern/kit/sound saves.
2. The "working project" slot `0x80` at sector `0x50000`: written by the background job "saveProjectToMmc(tempProject)" (`FUN_4004368e`, jobs name at `0x4023bb17`; DN2 1.11/1.12 `0x4003fdee`), which runs only when a project-state hash (`FUN_40041c66`) differs from the slot's stored value, and is called from the Brain constructor (every boot, 28,364 sectors, finding 24) and from the project-reload handler `FUN_40043f74` (callers `ProjectCache`, `KitActiveSettingsChanged`). Not timer-driven.
3. The persistent arena ("MRAM", `[0x4099d588, 0x41776c9c)`, 0xdd9714 bytes on DT2: COKi header 0x110 + the project container at `0x4099d698` + calibration, serial, test flags, MMC health), mirrored to the boot record sector `0x40000` or `0x48000` (alternating; next slot index in `DAT_402aafd8`, set by `FUN_400f04c8` at every boot). The live Project object is outside it (`0x41776c9c`).

Writers of the boot record:
- `FUN_400efe74` (1.17 `0x400effd8`, DN2 `0x400f1850`/`0x400f19b4`): installed through `FUN_40001ce0` in `FUN_400f0628` and run by interrupt vector 222 (`_DAT_40000378` at `0x40001a0e`-region handler reads `_DAT_40964d2c`). It sets a busy flag, polls the ESDHC, and if `DAT_431711d4` is set writes the whole arena (0x8000 bytes per chunk) with polled DMA to the next slot, then SOFTRST (`0x400f034a`) or spins. `DAT_431711d4` is set only by `FUN_400f0710`, called from a polling callback (`LAB_400cc7b0`, registered at boot) when GPIO `0xec094019` bit 3 reads set, and the callback then unregisters itself. So the flag means "the pin has been seen", and the emergency write is the power-loss path. What the pin is (supply good / power switch) is **[O]**.
- Vector 221 handler (`vector_221_handler`, callback `LAB_400efc1c`, registered in `FUN_400f0628`): sets GPIO `0xec09404b`, and unless the write is in progress, SOFTRSTs. **[O]** which physical event.
- `FUN_400f044a` (thunk `0x400d9e94`; 1.17 `0x400f05ae`; DN2 `0x400f1e26`/`0x400f1f8a`): the normal, thread-context writer. It writes the arena with the mutex-taking `FUN_400efce0` -> `FUN_4012e0c0` to the next slot, zeroes the first word of the other record (invalidates it) and sets `DAT_402aafd8 = -1`. Its only caller is the OS-update path `FUN_401073a2` (after the image validator `FUN_400d9e4c`, before "ERASING FLASH..." work and the flash write).

What serializes the live project into the arena container: `FUN_400df508(container, project, ?, parts, progress)` (parts mask `-1` = all). Callers: the boot decode (only when the container was upgraded), the job "Write project MRAM" (`FUN_40030c9c`, posted from the Brain constructor only when `_DAT_4099d584` says a new project was created at boot), `FUN_40041b1c` and `FUN_40043a30` (slot saves). I found NO call that serializes the live project into the arena in `FUN_400efe74`, in `FUN_400f044a` or in the OS-update path. **[O]** whether stock firmware keeps the arena current while the user edits (a hidden path through `FUN_400f4e52(project, -1)`, which returns the arena container for slot `-1`, callers `FUN_400f4e80`, `FUN_400f5050`, ProjectCopy), or whether unsaved edits are lost at stock power-off. This decides what a menu restart loses and needs one bounded emulator experiment: edit a pattern, run `FUN_40030c9c`, `FUN_400f044a`, then read sector `0x40000`/`0x48000` and compare with the live pattern; and the control without `FUN_40030c9c`.

If the menu soft-resets with no save, the lost state is whatever has not reached a slot, the working slot or the arena (edits since the last save and since boot, plus unsaved settings in the arena). Explicit project saves and sound/kit/pattern saves are safe.
Firmware function sequence that does what the firmware does before it flashes: `FUN_40030c9c` (serialize all parts to the arena; no arguments, returns 1, runs on a worker in the firmware) then `FUN_400f044a` (write the arena to the next boot record). Both take only singletons; `FUN_400f044a` writes 14.5 MB (a second or more, eMMC speed not measured) and must not run while a project operation or the "Update MMC Caches" job holds the card for write. Untested as a pair **[O]**.

## 3. Restart

**[D]** The reset is one byte: `RCM.RCR` at `0xEC090000` = `0x80` (SOFTRST). Sites (DT2 1.16): `0x40005652` (a function that starts at `0x40005608`: `move #0x2700,sr`; `jsr 0x400023f6` (waits for the console queues `0x40964d90`/`0x40964da0` and the UART8 transmitter, `0xEC070004` bit 3); `clr.l 0x48000000` (the first word of DDR through the uncached alias); 25 `nop`; `moveq #-128,d0; move.b d0,0xEC090000`; `rts`), `0x40001ab8` (inline, exception path), `0x400cbde6`/`0x400cbe44` (console commands `#REBOOT`, `#REBOOT_INTO_MAINTENANCE`, which write `0xB0B0DADA` to `0x48000000` first), `0x400efc84` (vector 221), `0x400f034a` (end of `FUN_400efe74`), `0x4013aaae` (end of the OS-update path `FUN_4013a978`: "Writing Flash", "Success! Rebooting"; 1.17 `0x4013ac54`, DN2 `0x40138e24`/`0x40139104`). Same functions and offsets on the four ports: reset function at `0x40005608` on all four; RCR sites 1.17 `0x40005652, 0x400cbf4a, 0x400efde8, 0x400f04ae, 0x4013ad8a, 0x40001ab8, 0x400cbfa8`; DN2 1.11 `0x40005652, 0x400ce27a, 0x400f1660, 0x400f1d26, 0x40138f5a, 0x40001ab8, 0x400ce216`; DN2 1.12 `0x40005652, 0x400ce3de, 0x400f17c4, 0x400f1e8a, 0x4013923a, 0x40001ab8, 0x400ce37a`.
`0x40005608` has no caller by Ghidra, by an absolute-address scan (refscan) and by a bsr/jsr-pc/branch/pointer scan of section 3 **[D]** (not a vtable slot either, since the pointer scan found no literal). Treat it as an unused stock helper: do not depend on it; the runtime inlines the same sequence.
The bootstrap (section 2, `0x80000b24`-`0x80000b44`) reads RSR (`0xEC090001`) bit 5 (soft reset) and compares `0x48000000` with `0xB0B0DADA`; only a match sets bit 5 (`0x20`) of the flags word it passes to MAIN OS, which enables the UART console (`DAT_4029e9b0 & 0x20`). With the word cleared, a SOFTRST is a normal boot. **[D]**
Clean to call from the UI task: yes, provided: (1) no ESDHC transfer is in flight (hold the eMMC mutex or finish the module-store write first, as `FUN_400f044a` has), (2) interrupts masked (`sr = 0x2700`), (3) `0x48000000` cleared (otherwise the next boot may start in console mode if it holds the magic), (4) the work to keep is saved first (section 2). Waiting on UART8 drain (`FUN_400023f6`) can spin forever if the console queue is stuck; the runtime can skip it (the OS-update path calls it too).

## 4. Parameter identity in stored data

**[D]** By storage slot / sound-array (mirror) index, never by the parameter code (pf_table row index).
- Sounds and kits: the 77-slot storage array is a fixed permutation of the runtime array (`FUN_400db930` save, table `0x40213640`; `FUN_400db24e` load, table `0x40213754`). Values are raw s16, no range check. The machine type byte is stored per kit track and per pool sound (finding 02).
- Parameter locks: DT2 `FUN_400dc4a6` (load) and `FUN_400dc6a0` (save), 0x102-byte entries `{id, track, 128 x s16}`. Save maps runtime index to storage id with the same permutation (`0x40213640`, FX track `0x40213470`); load maps back with `FUN_400dad24` (`0x40213754`, FX `0x40213588`, ids >= 0x4d skipped) and indexes `lock[track*0x47 + runtime_idx]`. No pf_table or code appears. The three values in the sound array that are "parameter ids" (runtime 4, 12, 20, mod/LFO destinations) go through the same tables: slots, not codes.
- Same code in other ports: DT2 1.17 `0x400dc60a` / `0x400dc804`; DN2 1.11 `0x400de51e` / `0x400de718` (ids < 0x6b, 0x65 runtime slots per track, `FUN_400dccc0`); DN2 1.12 `0x400de682` / `0x400de87c`.
- Consequence: run-time parameter codes may be allocated first-free per session; a module's parameter has its meaning from (machine type, knob slot 25..34 on DT2). `core/dynreg` already uses fixed slots (positional persistence, finding 30/33). **The permanent identity is the machine type byte (16..23)**, because it is stored in kits and pool sounds. If the type numbers are first-free over the selected set and the selection changes, saved tracks silently bind to another machine. The runtime should keep a stable type per module (for example the store records the type next to the module id) or refuse a selection that moves a type used by the saved kits. Global settings that might store a code (MIDI/NRPN maps) were not looked at **[O]**.

## 5. patchkit and the stock OS

**[D]** patchkit writes sections 3 (MAIN OS) and 7 (the SHARC boot stream, called BLOB in `out/sections`) only. Evidence: `packages/patchkit/src/apply.rs` calls `fw.replace(7, ...)` (line 1517) and `fw.replace(3, ...)` (line 1534) and nowhere else; `Firmware::replace` (`firmware.rs:80`) refuses ids 2, 4 and 8 ("bootstrap, updater, boot data are never changed"); every other section keeps its stored bytes verbatim, and the container is re-laid, summed and sealed (HMAC trailer) by `syx.rs`. Python side: `tools/patchkit/patchimg.py` refuses sections 2 and 4 by section number and by sha256; `patched_image.py` and `machinepatch` use `tools.firmware.inplace.patch_section(syx, 3, ...)`; `dsp_patch.py` calls `build.rebuild(..., {7: ...})` where unreplaced sections keep their stored bytes.
Section map (1.16): 2 = bootstrap (misnamed "DSP", version word `0x0201`, owns the STARTUP menu and "READY TO RECEIVE"), 3 = MAIN OS, 4 = UPDATER, 5 = META, 7 = SHARC boot stream, 8 = boot data. So the stock OS can always be sent again: the bootstrap validates only the content checksum and the HMAC and has no version comparison on that path (finding 01, "Recovery"); MAIN OS has only a floor on the build string (`006/`), which 1.15C and 1.16 pass. The one irreversible operation, the bootstrap upgrade, happens only when the incoming section 2 version is higher than the running one, and patchkit never changes section 2. Section 5 (META) is not in the refusal list; patchkit does not replace it, but nothing enforces it **[O]** (only the refusal of 2, 4, 8 is code).
