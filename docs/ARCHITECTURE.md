# Architecture

This file says how the modules are layered, what each layer may depend on, and how a new device or firmware version fits. `tools/devtools/layercheck.py` enforces the rules (`mise run check:layers`).

## Layers

```text
 content module     machines, effects, tools        (modules/machines, fx, tools; .dkm files)
 app                menus and screens               (modules/core/apps)
       |  <dk/...> headers and imports               the SDK contract: sdk/
       v
 SDK contract       sdk/sdk.toml, sdk/include, sdk/asm: what a module may call and must provide
       |
       v
 runtime            loads .dkm files, links their imports, owns store, selection and policy (modules/core/runtime)
       |  exported functions (dkrt.h) and optional symbols
       v
 adapters           one per firmware plug-in point; they hook, wrap and fix the firmware (modules/core/adapters)
       |  generated bindings (dk_fw_*, crate dkfw)
       v
 firmware           stock Elektron code, found by anchors (devices/ports, devices/fw)
```

A module never reaches past the layer under it. Everything that depends on the device or the firmware version sits in adapters, device profiles and anchors, not in the SDK or in modules.

`core/expansion` is the reset-time installer: it runs at reset and copies all patched-in code to its place. `modules/core/fw` holds the generated firmware bindings (a library, not a module).

## Roles

| Layer | Folder | `role` | Runs | May depend on |
| --- | --- | --- | --- | --- |
| Runtime | `modules/core/runtime` | `runtime` | At boot and in the UI and block loops | Firmware bindings, SDK crate `dkrt-sdk`, adapters through optional symbols |
| Installer | `modules/core/expansion` | `installer` | At reset, once | Firmware bindings |
| Firmware bindings | `modules/core/fw` | none (not a module) | Never; generated by `patchkit gen` from `devices/fw/` | Anchors |
| Adapter | `modules/core/adapters/NAME` | `adapter` | Inside firmware hooks, in the firmware's contexts | Firmware bindings, runtime exports, other adapters' headers |
| App | `modules/core/apps/NAME` | `app` | In the task context, called by an adapter | SDK, `dkrt.h`, `dk_ui_core.h` |
| Content module | `modules/machines`, `fx`, `tools`, `tests/fixtures/modules` | none | Loaded at run time from the card (a `.dkm`) | SDK only |
| SDK | `sdk/` | none | Not code that runs; the contract | Nothing |

`modules/core/remote-open` is an adapter that stays directly under `modules/core` until it is deleted.

## Rules

`layercheck` reads manifests, sources and built objects. It builds nothing and takes well under a second.

1. **Roles.** Every module under `modules/core` has `role` in `[module]`, and the role fits the folder: `adapters/` is `adapter`, `apps/` is `app`, `runtime/` is `runtime`, `expansion/` is `installer`.
2. **Sources.** Content modules and apps include only their own files and the SDK (`<dk/...>`, `sdk/asm`). An app may also include `dkrt.h` and `dk_ui_core.h`. Only runtime, installer and adapters include `dk_fw_*` headers or depend on the `dkfw` crate. C, ColdFire and SHARC assembly (`#include`, `.include`) and Rust (`dkfw`, path dependencies) are checked.
3. **Objects.** The undefined symbols of the built objects of apps and content modules are SDK imports (`sdk/sdk.toml` `[[import]]`), `dkrt_*`, `dk_ui_*`, `dk_app_*` or the SHARC externs the SDK documents. They never name a firmware anchor (`cf.*`, `dsp.*`, `hook.*`, `pk.*`), and `[object.externs]` never maps a symbol to one.
4. **Apps do not patch.** An app has no `[[op]]` and no `[[claim]]`. If an app needs a firmware hook, the adapter that owns that plug-in point installs the hook and calls the app through an optional symbol (`dk_app_*`).

Exceptions are listed in `layercheck.py` with a reason: `digikit/master-gain`, `digikit/master-drive` and `test/registry-demo` patch the firmware themselves (they are patchkit's examples of a patched-in effect and a hook), and `test/ui-demo` stands in for an app.

Run it:

```sh
mise run check:layers          # or: uv run python -m tools.devtools.layercheck
```

Each violation prints `file:line: rule: what is wrong. Instead: what to do.` The gate runs it in `python-tests` (with ruff, mypy and pathcheck) whenever modules, the SDK or the firmware declarations change; `mise run test:changed` runs it too.

## How a new device or firmware version fits

A new firmware version of a known device:

1. Add the anchors to `devices/ports/` (they resolve by hash) and check the declarations in `devices/fw/`.
2. Run `patchkit gen`. The bindings in `modules/core/fw` follow.
3. Fix what changed in the adapters. The adapters hide the difference; no SDK header, no content module and no app changes.

A new device:

1. Add the device profile (`devices/NAME.toml`): limits, patch sets, panel, storage and the values the adapters read (`docs/design/device-data.md`).
2. Add its ports and, where its firmware differs, device-specific adapter sources (`src/cf/NAME/`, `src/dsp/NAME.s`) behind the same adapter API.
3. Keep the SDK contract. A content module that builds against the SDK loads on the new device when the runtime reports the contract version.

## Where the device specifics live

| What | Where |
| --- | --- |
| Firmware addresses and hook sites | `devices/ports/` (anchors by hash) |
| Firmware function and structure declarations | `devices/fw/`, generated into `modules/core/fw` |
| Limits, patch sets, panel, storage | `devices/*.toml` (device profiles) |
| Code that hooks or wraps firmware | `modules/core/adapters/*` |
| The module contract | `sdk/` (device-neutral) |

## Worked example: the UI path

A menu or screen of an app or module goes through these steps:

1. **Module.** A module calls `dk_ui_menu_new`, `dk_ui_text`, `dk_ui_open` and the other calls of `<dk/ui.h>` (`sdk/include/dk/ui.h`). It knows no firmware.
2. **Runtime.** The runtime links the module's imports when it loads the `.dkm` (the link of the UI imports through the runtime is planned; today patchkit links the `dk_ui_*` symbols of `core/ui` when it patches an app in).
3. **Adapter `core/ui`.** `modules/core/adapters/ui` implements the calls. It builds the firmware's own views (`VerticalMenuView`, list and text views) through the generated bindings (`dk_fw_view.h`, `dk_fw_menu.h`) and keeps their state.
4. **Firmware views.** The firmware draws and handles the keys.

The SETTINGS entry shows the rule for hooks. `core/ui` owns the hook at the end of the SETTINGS list rebuild (`cf.menu.hook.settings_list.tail`). It calls the optional symbol `dk_app_settings_rows(settings_menu)` (declared in `dk_ui_core.h`). The app `core/digikit-menu` implements it with `dk_ui_stock_row` and adds the DIGIKIT row. The app has no hook, no claim and no firmware include. When no app is in the image, patchkit resolves the symbol to 0 and the hook does nothing.

The same holds for card reads: the INFO page of the menu gets the module header from `dkrt_module_header` of the runtime, which does the card read in its own buffer.
